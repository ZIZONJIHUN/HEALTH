구글 로그인 붙이기

코드는 다 올라가 있습니다. 남은 건 Supabase와 Google Cloud 쪽 설정인데, 이건 콘솔에서 직접 눌러야 하는 일이라 제가 대신할 수 없습니다. 아래 순서대로 하시면 됩니다.

0 / 19
01

Supabase 프로젝트

supabase.com → 프로젝트 → SQL Editor

  1. Supabase 프로젝트를 만듭니다. 이미 있으면 건너뜁니다.

    리전은 아무거나 괜찮습니다. 무료 플랜으로 충분합니다.

  2. SQL Editor에서 마이그레이션 세 개를 순서대로 실행합니다.

    파일하는 일
    0001_search_cache.sql검색 캐시 테이블
    0002_api_budget_and_cache_hygiene.sql일일 호출 예산
    0003_profiles.sql로그인에 필요한 것 — 프로필·역할·가입 트리거·RLS

    저장소의 supabase/migrations/ 에 있습니다. 파일 내용을 그대로 붙여넣고 Run. 세 개 다 여러 번 실행해도 안전하게 써뒀습니다.

  3. Project Settings → API 에서 값 세 개를 복사해 둡니다.

    콘솔에서 보이는 이름쓰이는 곳
    Project URL로그인 + 캐시
    anon public로그인 (브라우저에 들어감)
    service_role캐시만 (서버 전용)

    service_role 키는 RLS를 통째로 우회합니다. 브라우저에 절대 들어가면 안 되고, 코드에서도 src/lib/supabase/service.ts 한 곳에 가둬뒀습니다.

02

Google Cloud에서 OAuth 클라이언트 발급

console.cloud.google.com → API 및 서비스

  1. OAuth 동의 화면을 설정합니다. User Type은 외부, 앱 이름은 헬스 쇼츠 정도면 됩니다.

    게시 상태는 테스트로 둬도 됩니다. 그 경우 테스트 사용자에 본인 구글 계정을 반드시 추가하세요. 안 하면 본인 계정으로도 로그인이 거부됩니다.

  2. 사용자 인증 정보 → 사용자 인증 정보 만들기 → OAuth 클라이언트 ID, 유형은 웹 애플리케이션.

  3. 승인된 리디렉션 URI 에 이것을 넣습니다. <project> 자리에 본인 Supabase 프로젝트 ref를 넣으세요.

    https://<project>.supabase.co/auth/v1/callback

    여기는 우리 앱 주소가 아니라 Supabase 주소입니다. 구글은 Supabase로 돌려보내고, Supabase가 다시 우리 앱으로 돌려보냅니다.

  4. 만들어진 클라이언트 ID와 클라이언트 보안 비밀번호를 복사해 둡니다.

03

Supabase에 구글 연결

Supabase → Authentication

여기가 제일 많이 헷갈리는 곳입니다

양쪽 콘솔에 "리디렉션 URL"처럼 생긴 칸이 하나씩 있는데, 서로 다른 주소가 들어갑니다. 반대로 넣으면 로그인 버튼을 눌렀을 때 구글이 redirect_uri_mismatch를 띄웁니다.

Google Cloud → 승인된 리디렉션 URI 구글이 돌려보낼 곳 = Supabase https://<project>.supabase.co/auth/v1/callback
Supabase → Redirect URLs Supabase가 돌려보낼 곳 = 우리 앱 http://localhost:3000/**

  1. Authentication → Providers → Google 을 켜고, 02에서 받은 클라이언트 ID와 보안 비밀번호를 넣고 저장합니다.

  2. Authentication → URL Configuration → Site URL 에 이것을 넣습니다.

    http://localhost:3000

  3. 같은 화면의 Redirect URLs 에 이것을 추가합니다.

    http://localhost:3000/**

    끝의 /** 가 있어야 /auth/callback 으로 돌아올 수 있습니다. 나중에 배포하면 배포 도메인도 같은 방식으로 추가하세요.

04

.env.local 채우기

프로젝트 루트 · git에 올라가지 않는 파일

  1. 01에서 복사해둔 값 세 개를 넣습니다. YOUTUBE_API_KEY 는 이미 들어 있습니다.

    NEXT_PUBLIC_SUPABASE_URL=https://<project>.supabase.co NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon public 키> SUPABASE_SERVICE_ROLE_KEY=<service_role 키>

    NEXT_PUBLIC_ 이 붙은 둘은 브라우저에 들어갑니다. 공개돼도 안전합니다 — anon 키로 할 수 있는 일은 RLS가 정한 범위뿐입니다.

05

브라우저 열기 전에 점검

터미널

  1. 설정이 실제로 섰는지 확인합니다.

    npm run auth:check

    마이그레이션 0003 미실행, anon 키 오타, URL 오타를 여기서 잡습니다. 하나 더 보는 게 있는데 — 로그인하지 않은 상태로 profiles 를 조회해서 행이 나오면 실패로 처리합니다. RLS가 열려 있다는 뜻이라 그냥 넘기면 안 되는 종류입니다.

    성공 메시지가 뜨면 다음으로. 실패하면 메시지에 고칠 곳이 적혀 있습니다.

06

실제 로그인 확인

npm run dev → localhost:3000/account

여기부터는 자동 테스트가 덮지 못하는 부분입니다. 진짜 구글 계정과 동의 화면이 필요해서 CI에서 돌릴 수 없습니다. 자동 테스트가 보는 것은 비로그인 화면, 실패 안내, 콜백이 외부 주소로 보내지 않는지까지입니다.

  1. /account 에서 구글로 로그인 버튼이 활성이다.

    회색으로 비활성이면 .env.local 을 다시 보세요. dev 서버 재시작도 필요합니다.

  2. 누르면 구글 동의 화면이 뜨고, 동의하면 /account 로 돌아와 이메일이 보인다.

  3. 개발자도구 → Application → Cookies 에 sb- 로 시작하는 쿠키가 있다.

  4. 새로고침해도 로그인이 유지된다.

  5. 로그아웃한 뒤 다시 로그인 → 구글 동의 화면에서 취소하면 /account 로 돌아와 안내가 뜨고 앱은 멀쩡하다.

    에러 화면이 뜨면 안 됩니다. 로그인은 부가 기능이지 앱의 전제가 아닙니다.

  6. Supabase Table Editor → profiles 에 방금 가입한 행이 있다.

    없으면 0003 마이그레이션을 실행하지 않은 것입니다. 가입 트리거가 만드는 행입니다.

  7. 로그아웃한 뒤 /routines 에 루틴이 그대로 있다.

    놓치기 쉬운데 중요합니다. 로컬 루틴은 계정이 아니라 브라우저의 것이라, 로그인해본 적 있다는 이유로 사라지면 안 됩니다. 미리 루틴 하나를 만들어 두고 확인하세요.

세션 갱신은 따로 확인해야 합니다

토큰은 1시간 만료입니다. 갱신이 안 되면 한 시간 뒤 조용히 로그아웃되는데, 한 시간을 기다리지 않으면 드러나지 않습니다.

Supabase → Authentication → Sessions 에서 JWT 만료를 60초로 줄이고, 1분 지난 뒤 새로고침했을 때 로그인이 유지되는지 보세요. 확인 후 원래 값으로 되돌립니다. 유지되지 않으면 proxy.ts 의 matcher 를 의심하면 됩니다.
