# 헬스 쇼츠 + 짐웨어 추천 서비스 설계

작성일: 2026-07-25
저장소: https://github.com/ZIZONJIHUN/HEALTH.git

## 1. 목적

운동 이름을 검색하면 해당 운동의 숏폼 영상을 **외부 사이트로 이동하지 않고 웹 내부에서** 연속 재생하고, 운동에 어울리는 헬스 의류를 브랜드·핏·부위별로 분류해 추천하는 모바일 친화 다크모드 웹 서비스.

## 2. 범위 판단

### 포함

- 운동 이름 검색 및 부위별 카테고리 선택
- 검색 결과 썸네일 그리드 → 전면 세로 스와이프 쇼츠 피드
- 헬스 의류 카탈로그 (브랜드·핏·부위 3축 필터)
- 관리자 상품 등록·수정 (웹 UI)
- 사용자 로그인 및 즐겨찾기 (영상·의류)

### 제외 (근거)

| 제외 항목 | 근거 |
|---|---|
| Instagram Reels / TikTok 검색 연동 | 키워드 검색 공개 API가 없음. 개별 URL을 사람이 직접 입력하는 방식만 가능하므로 "검색 → 자동 연속 재생"이 성립하지 않는다. |
| 오픈마켓(쿠팡·네이버) 상품 자동 연동 | 제휴 심사가 선행되어야 하고, 검색 결과 품질이 낮아 "컴프레션/머슬핏" 같은 분류 정확도를 보장할 수 없다. |
| 라이트모드 토글 | 다크 전용으로 확정. 두 테마를 유지하는 비용이 값어치를 넘는다. |
| 관리자 승격 UI | 권한 상승 취약점 표면을 만든다. 관리자가 한두 명인 규모에서는 Supabase 콘솔에서 직접 `profiles.role`을 변경한다. |
| 네이티브 앱 (React Native) | 반복 속도가 느리고 YouTube 재생에 WebView 신뢰가 필요하다. 웹을 PWA로 감싸 홈화면 설치까지 커버한다. |

## 3. 기술 구성

| 레이어 | 선택 |

## 4. 화면 구조

### 하단 탭바 4개

| 탭 | 내용 |
|---|---|
| 운동 | 중앙 검색창 + 부위별 카테고리 칩 → 검색 결과 썸네일 2열 그리드 |
| 의류 | 브랜드·핏·부위 필터 바 + 상품 카드 그리드 |
| 저장 | 즐겨찾기. 영상 / 의류 두 개 서브탭 |
| 내 정보 | 로그인·로그아웃. 관리자에게만 상품 관리 진입 노출 |

부위별 카테고리: 가슴, 등, 어깨, 하체, 팔, 코어, 전신

### 전면 피드는 탭이 아닌 오버레이 라우트

그리드에서 썸네일을 탭하면 탭바가 없는 전체화면 라우트 `/feed?q=<검색어>&i=<인덱스>`가 열린다. 뒤로가기로 그리드의 같은 스크롤 위치로 복귀한다.

**근거:** 피드가 URL을 가지면 링크 공유와 새로고침이 정상 동작한다. 모달 상태로만 두면 두 가지가 모두 깨진다.

### 전면 피드 재생 방식

- CSS `scroll-snap`으로 세로 한 칸씩 스냅
- `IntersectionObserver`로 **현재 슬라이드와 앞뒤 1개만 iframe을 마운트**하고 나머지는 썸네일 이미지로 유지
  - 근거: 12개 iframe을 동시에 띄우면 모바일에서 즉시 버벅인다
- iframe 파라미터: `playsinline=1`, `mute=1`, `loop=1`, `rel=0`, `modestbranding=1`
  - `playsinline=1`은 iOS가 재생을 강제 전체화면으로 빼앗는 것을 막는다
  - `mute=1`은 선택이 아니다. 브라우저 정책상 모바일에서 음소거 자동재생만 허용된다. 사용자가 탭해서 소리를 켜는 흐름으로 설계한다.
- 검색 시 `videoEmbeddable=true`로 임베드 금지 영상을 애초에 제외

## 5. YouTube 연동

### 쿼터 제약

| 호출 | 비용 |
|---|---|
| `search.list` | 100 units |
| `videos.list` (최대 50개 일괄) | 1 unit |
| 검색 1회 합계 | 101 units |
| 일일 무료 쿼터 | 10,000 units → 약 99회 검색 |

99회는 개발 중 반나절에 소진된다. 캐시는 선택이 아니라 필수 요건이다.

### 쇼츠 판별

API에 "쇼츠만" 필터는 존재하지 않는다. 2단계로 근사한다.

1. `search.list`: `q=<운동명>`, `type=video`, `videoDuration=short`(4분 미만), `videoEmbeddable=true`, `regionCode=KR`, `relevanceLanguage=ko`, `maxResults=25`
2. 반환된 ID를 `videos.list(part=contentDetails)`로 일괄 조회해 실제 길이를 파싱하고 **180초 이하만 남긴다** (YouTube 공식 쇼츠 상한)

**세로/가로 비율은 API로 알 수 없다.** `youtube.com/shorts/{id}` 요청이 리다이렉트되는지로 정확히 판별할 수 있으나 **비공식 동작이므로 언제든 막힐 수 있다.** 따라서 이는 있으면 좋은 보정 단계로만 두고, 실패하면 조용히 무시하고 길이 기준 결과를 사용한다. 서비스 정상 동작이 이 트릭에 의존해서는 안 된다.

### 캐싱

- `search_cache` 테이블에 정규화된 검색어를 키로 결과 JSON 저장, TTL 7일
- 정규화: 앞뒤 공백 제거, 소문자화, 연속 공백 1칸으로 축약
- 인기 운동 20개는 미리 캐시에 시드 → 쿼터 소진일에도 주요 운동은 정상 동작
- 메모리가 아닌 DB에 둔다. Vercel 인스턴스가 여러 개로 늘어도 캐시가 공유되어야 한다.

## 6. 데이터 모델

```
brands        id, name, name_ko, logo_url, site_url, sort_order

products      id, brand_id -> brands.id
              name, name_ko, description
              part      : 'top' | 'bottom' | 'gear'
              fit       : 'compression' | 'muscle' | 'over' | 'singlet' | null
              gear_type : 'strap' | 'knee_sleeve' | 'belt' | 'glove' | 'other' | null
              tags      : text[]
              image_url, image_path, price, currency
              purchase_url
              is_published, created_at, updated_at

profiles      id -> auth.users.id, role: 'user' | 'admin'

favorites     id, user_id -> auth.users.id
              kind: 'video' | 'product'
              product_id -> products.id        (kind='product')
              video_id, video_meta jsonb       (kind='video')
              created_at
              UNIQUE(user_id, kind, product_id, video_id)

search_cache  query_key (PK), payload jsonb, created_at
```

### 설계 판단

- **`fit`과 `part` 2축 분리** — 컴프레션 상의와 컴프레션 하의가 모두 존재하므로 한 축으로는 표현할 수 없다. 두 축이면 "컴프레션 + 하의" 조합 필터가 자연스럽게 나온다. 용품(`part='gear'`)은 핏 개념이 없어 `fit`이 `null`이고 대신 `gear_type`을 쓴다.
- **`fit`·`part`는 문자열 코드, 브랜드는 별도 테이블** — 핏과 부위는 거의 늘어나지 않는다. 브랜드는 계속 추가되고 로고·사이트 링크 같은 부가 정보가 붙는다.
- **즐겨찾기 영상에 `video_meta` 동봉** — 영상은 우리 DB에 없는 외부 리소스다. 제목·썸네일을 저장하지 않으면 저장 목록을 열 때마다 YouTube API를 호출해 쿼터를 태운다.
- **이미지는 `image_url`(외부 참조)과 `image_path`(Supabase Storage 업로드) 둘 다 지원** — 저작권 이슈(9절) 발생 시 코드 변경 없이 교체할 수 있어야 한다.

### 접근 권한 (RLS)

| 테이블 | 읽기 | 쓰기 |
|---|---|---|
| brands, products | 누구나 (`is_published = true`만) | admin |
| favorites | 본인 것만 | 본인 것만 |
| search_cache | 서버(service role)만 | 서버만 |
| profiles | 본인 것만 | 본인 (`role` 변경은 서버만) |

## 7. 의류 필터 UI

상단 3개 필터 그룹을 칩으로 배치. **그룹 안에서는 다중 선택(OR), 그룹 사이는 AND.**

```
브랜드  [전체] [언더아머] [덤브스트럭] [HDEX] [짐샤크] [나이키]
핏      [전체] [컴프레션] [머슬핏] [오버핏] [싱글렛]
부위    [전체] [상의] [하의] [용품]
```

예: `(짐샤크 OR 나이키) AND (컴프레션) AND (상의)`

선택 상태는 URL 쿼리에 실어 필터가 걸린 화면을 그대로 공유·복원할 수 있게 한다.

### 상품 카드 구성

대표 이미지, 브랜드명, 상품명, 특징 태그, 구매 링크 버튼, 즐겨찾기 토글.

## 8. 오류 처리

| 상황 | 동작 |
|---|---|
| 쿼터 초과 (403 `quotaExceeded`) | 캐시된 결과로 폴백 + "오늘 검색 한도에 도달했어요" 배너. 앱은 계속 사용 가능 |
| 검색 결과 0개 | 추천 검색어 칩 표시 (오타·영문 검색 유도) |
| 특정 영상 임베드 실패 | 해당 슬라이드 자동 스킵 |
| 네트워크 실패 | 재시도 버튼, 이전 결과 유지 |
| 관리자 아닌 사용자가 관리 경로 접근 | 서버에서 `profiles.role` 확인 후 404 응답 |

## 9. 알려진 리스크

**상품 이미지 저작권** — 브랜드 공식 상품컷을 그대로 올려 쓰는 것은 저작권 리스크가 있다. 개인 학습·포트폴리오 수준에서는 실질적 문제가 거의 없으나, 공개 서비스로 키운다면 제휴 프로그램 제공 이미지나 직접 촬영본으로 교체해야 한다. 데이터 모델이 URL 참조와 직접 업로드를 모두 지원하므로 교체 시 코드 변경은 필요 없다.

**비공식 쇼츠 판별** — 5절의 `/shorts/{id}` 리다이렉트 검사는 언제든 막힐 수 있다. 보정 단계로만 두고 실패를 무시하도록 설계했다.

## 11. 테스트 전략

- **단위 (Vitest)** — ISO8601 길이 파서, 쇼츠 필터, 캐시 키 정규화, 의류 3축 필터 쿼리 빌더. 모두 순수 함수로 분리해 테스트한다.
- **YouTube API는 MSW로 목킹** — 테스트가 실제 쿼터를 소모하지 않아야 한다.
- **E2E (Playwright)** — 검색 → 그리드 → 피드 진입 → 뒤로가기 시 스크롤 위치 복원, 의류 필터 조합, 관리자 상품 등록, 즐겨찾기 토글.

## 12. 구현 순서

기능별 3단계 분할. 각 단계가 끝나면 배포 가능한 상태가 된다.

| 단계 | 범위 | 완료 시점의 상태 |
|---|---|---|
| 1 | 프로젝트 셋업, 운동 검색, 썸네일 그리드, 전면 스와이프 피드, 검색 캐시 | DB·로그인 없이 배포되어 폰에서 검색·재생 가능 |
| 2 | Supabase 스키마 + RLS, 의류 카탈로그·필터, 관리자 상품 관리 | 상품을 웹에서 등록하고 필터링 가능 |
| 3 | 로그인, 즐겨찾기 (영상·의류) | 저장 목록이 기기 간 동기화 |

4절의 탭바 4개는 최종 형태다. 단계별로는 아래처럼 점진적으로 채운다.

| 단계 | 노출되는 탭 |
|---|---|
| 1 | 운동 (나머지 탭은 렌더하지 않음) |
| 2 | 운동, 의류 |
| 3 | 운동, 의류, 저장, 내 정보 |

단계 1은 인증·상품 DB 없이 시작하지만 검색 캐시는 필요하므로, Supabase 프로젝트를 만들고 `search_cache` 테이블만 먼저 생성한다.
