# 루틴 동기화 · 운동 기록 설계

작성일: 2026-10-31
범위: 인증 설계(`2026-09-19-auth-foundation-design.md`)의 **B. 루틴 동기화**와, 그 위에
얹는 새 기능 **운동 기록**. C(즐겨찾기)·D(의류)는 다루지 않는다.

## 1. 왜 지금인가

로그인(A)은 머지됐지만 로그인해도 달라지는 것이 없다. 설정 화면도 루틴 화면도
"루틴은 이 브라우저에만 저장돼요"라고 말한다. A 설계가 경고한 상태 — "왜 로그인했는지
알 수 없다" — 가 지금이다. B 가 붙어야 로그인이 의미를 갖는다.

운동 기록은 이 앱을 "영상 보는 앱"에서 "운동하러 오는 앱"으로 바꾸려는 것이다. 루틴을
끝까지 돌리면 이미 "루틴을 끝냈어요"가 뜬다. 그 순간을 남기고, 쌓인 것을 보여준다.
기기를 바꾸면 사라지는 기록은 의미가 반감되므로 B 의 동기화 구조 위에 둔다.

## 2. 목표 · 비목표 · 반목표

**목표**
- 로그인한 사용자의 루틴이 기기 사이에서 같아진다.
- 로그인하기 전에 만든 루틴이 첫 로그인 때 사라지지 않고 계정으로 들어간다.
- 루틴을 끝까지 돌리면 그날 운동한 것으로 기록되고, 루틴 화면에서 이번 주·연속 일수·
  이번 달 횟수를 본다.
- 비로그인 사용자는 지금과 똑같이 쓴다. 기록도 이 브라우저에 남는다.

**비목표**
- 실시간 동기화(다른 기기에서 고친 것이 열린 화면에 즉시 반영). 다음에 앱을 열거나
  포커스가 돌아올 때 맞춰지면 충분하다.
- 오프라인 편집의 완전한 충돌 해결. 루틴 단위 last-write-wins 로 족하다(4.3).
- 세트·휴식 타이머. 논의 끝에 빠졌다.
- 기록 편집·삭제 UI, 기록 상세 화면, 통계 차트.
- 검색 피드에서 본 것을 운동 기록으로 치는 것. 기록은 루틴에서만 생긴다.

**반목표** — 동작해도 이렇게 되면 실패다
- **로그인하는 순간 루틴이 사라지거나 중복된다.** 이 기능의 신뢰가 여기서 결정된다.
- **다른 사람의 루틴이 내 계정에 섞인다.** 공용 PC 에서 A 가 로그아웃하고 B 가
  로그인했을 때 A 의 루틴이 B 에게 합쳐지면 안 된다.
- 비로그인 사용자에게 가입 벽이 생긴다. 로그인은 빼앗지 않고 더한다(A 설계 원칙).
- 동기화가 실패했을 때 화면에는 저장된 것처럼 보이고 나중에 사라진다. routines.ts 가
  이미 지키고 있는 "조용한 실패 금지" 원칙을 동기화에도 적용한다.
- 루틴을 재생하거나 열 때 YouTube 쿼터를 쓴다. 메타데이터는 지금처럼 통째로 저장한다.

## 3. 지금 상태

- `features/routines/routines.ts` — localStorage(`health-shorts:routines:v1`) +
  `useSyncExternalStore`. 함수는 전부 동기(sync)다. 저장 성공 여부를 반환한다.
  삭제는 실행 취소(`deleteRoutine` → `restoreRoutine`)로 되돌린다.
- `Routine = { id, name, createdAt, items: ShortVideo[] }`. id 는 클라이언트가 만든다
  (`r<시간36진수><난수>`).
- Supabase: `profiles`(트리거 생성, 본인 읽기만), 클라이언트 셋(`service` / `server` /
  `browser`). 사용자 데이터에는 `service` 를 쓰지 않는다(A 설계 3절).
- CSP `connect-src` 에 Supabase 오리진이 이미 들어 있다.
- 루틴 재생 끝 감지(`useVideoEnded`)는 실패할 수 있다고 문서화돼 있다.

## 4. 루틴 동기화

### 4.1 원칙: 로컬 우선, 서버로 밀고 당긴다

화면은 지금처럼 localStorage 만 읽는다. 동기 API 와 `useSyncExternalStore` 를 그대로
둔다 — 모든 화면이 이 위에 있고, 비로그인 경로가 바뀌지 않는다.

로그인 상태면 그 위에 동기화 계층이 붙는다.
- **당기기(pull)**: 앱이 뜰 때, 로그인 직후, 탭에 포커스가 돌아올 때 서버의 루틴을
  받아 로컬과 합친다.
- **밀기(push)**: 로컬에서 루틴이 바뀔 때마다 바뀐 루틴을 서버에 upsert 한다.

### 4.2 데이터 모양

**로컬** — `Routine` 에 필드를 더하고 저장 키를 `v2` 로 올린다. v1 은 읽어서 변환한다.

| 필드 | 뜻 |
|---|---|
| `updatedAt: number` | 마지막 변경 시각(ms). 병합 기준 |
| `deletedAt: number \| null` | 지운 시각. 지운 루틴도 동기화가 끝날 때까지 남긴다(묘비) |
| `owner: string \| null` | 이 루틴이 속한 사용자 id. 비로그인 때 만든 것은 null |
| `dirty: boolean` | 서버에 아직 반영되지 않았다 |

화면용 읽기(`loadRoutines`)는 `deletedAt` 이 있는 것과 **다른 사용자 소유인 것**을
걸러서 지금과 같은 `Routine[]` 을 준다. 화면 코드는 새 필드를 몰라도 된다.

**서버** — `public.routines`

| 열 | 타입 | 비고 |
|---|---|---|
| `user_id` | uuid | `auth.users` 참조, on delete cascade |
| `id` | text | 클라이언트가 만든 id. 기본키는 `(user_id, id)` |
| `name` | text | 1~60자 |
| `items` | jsonb | `ShortVideo[]`. 배열, 최대 100개 |
| `position` | int | 목록 순서 |
| `created_at` | timestamptz | |
| `updated_at` | timestamptz | 클라이언트가 보낸 `updatedAt` |
| `deleted_at` | timestamptz null | 묘비 |

운동 항목을 별도 표로 쪼개지 않는다. 루틴 하나가 항상 통째로 읽히고 쓰이며, 순서 변경이
"배열 교체"로 끝난다. 정규화로 얻는 것이 없다.

RLS: `user_id = auth.uid()` 인 행만 select/insert/update. delete 정책은 열지 않는다
(묘비로 지운다). `user_id` 를 클라이언트가 바꿀 수 없게 insert/update 의 with check 도
같은 조건으로 건다.

**상한(Claude 의 판단)** — 인증된 사용자가 행을 무제한으로 쌓는 경로를 닫는다.
- 살아 있는 루틴(`deleted_at is null`) 200개까지. 트리거로 건다. 묘비는 세지 않는다 —
  세면 만들고 지우기를 200번 한 사용자가 영영 새 루틴을 못 올린다.
- 묘비는 30일이 지나면 같은 사용자의 다음 쓰기 때 트리거가 지운다. cron 을 두지 않는다.
  30일 넘게 켜지 않은 기기가 지운 루틴을 되살릴 수 있지만, 그 기기에서는 그 루틴이
  살아 있었으므로 사용자가 보기에 이상하지 않다.
- 같은 제약(이름 1~60자, 항목 100개, 살아 있는 루틴 200개)을 **로컬에서 먼저 막는다.**
  담기에 'full' 결과를 더해 "한 루틴에는 100개까지 담을 수 있어요"를 보여준다. v1→v2
  변환 때 60자를 넘는 이름은 자른다.

**영구 거부** — 그래도 서버가 제약 위반(check·트리거 오류)으로 거절하면 일시 실패와
구분해 `syncError: 'rejected'` 로 표시하고 다시 시도하지 않는다. 상태 줄은 "OO 루틴은
계정에 저장할 수 없어요" 와 이유를 보여준다. 루틴을 고치면(`updatedAt` 이 바뀌면) 표시를
지우고 다시 민다. 네트워크·인증 오류는 일시 실패로 보고 재시도한다.

### 4.3 병합 규칙

같은 id 끼리 `updatedAt` 이 큰 쪽이 이긴다(루틴 단위 last-write-wins). 묘비도 같은
규칙을 따른다 — 지운 것이 나중이면 지워지고, 고친 것이 나중이면 되살아난다.

한쪽에만 있는 루틴은 그대로 남는다. 이긴 쪽이 로컬이면 `dirty` 로 표시해 밀어 올린다.

항목 단위 병합은 하지 않는다. 두 기기에서 같은 루틴에 서로 다른 영상을 거의 동시에
담으면 한쪽이 진다. 한 사람이 쓰는 앱에서 드문 일이고, 항목 단위 병합의 복잡도에
비해 얻는 것이 적다.

### 4.4 로그인 · 로그아웃 · 계정 전환

| 상황 | 동작 |
|---|---|
| 로그인 상태인데 이 브라우저에 `owner: null` 루틴이 있음 | **묻는다**: "로그인 전에 이 브라우저에서 만든 루틴 N개가 있어요. 내 계정으로 가져올까요?" [가져오기] [두기]. 가져오면 이 사용자 소유로 바꾸고 `dirty` 로 밀어 올린다 |
| 로그인 상태로 앱을 엶 | 당기고 합친다. `dirty` 가 남아 있으면 민다 |
| 로그인 세션이 끝남(로그아웃 버튼, 세션 만료, 다른 탭의 로그아웃 — 이유를 가리지 않는다) | `dirty` 를 먼저 밀어 본다(최대 수 초). 그다음 이 사용자 소유 루틴 중 **반영된 것은 지우고, 못 민 것만 남긴다** |
| 다른 사용자로 로그인 | 이전 사용자 소유로 남은 것(=못 민 변경)은 보이지 않고 합쳐지지도 않는다. 이전 사용자가 다시 로그인하면 마저 민다 |

**흡수를 묻는 이유(Claude 의 판단)**: 묻지 않고 흡수하면 공용 PC 에서 익명 손님이
만든 루틴이 다음에 로그인한 사람의 계정으로 영구히 들어간다. "로그인하는 순간에만
흡수"로 좁히면 배포 시점에 이미 로그인해 있던 사용자 — v1 루틴이 변환 후 `owner: null`
이 된다 — 에게 그 순간이 다시 오지 않아 루틴이 영영 동기화되지 않는다. 그래서 조건이
보이는 동안(로그인 상태 + `owner: null` 이 있음) 묻는다. [두기]를 고르면 그 루틴은
이 브라우저 전용으로 남아 로그인 중에는 보이지 않고 로그아웃하면 다시 보인다. 같은
기기에서 다시 묻지 않도록 "두기"를 선택한 사용자 id 를 기억한다.

**세션 종료를 한 경로로 다루는 이유(Claude 의 판단)**: 로그아웃 버튼 안에서만 처리하면
세션 만료나 다른 탭 로그아웃에서 정리가 일어나지 않는다. 루트의 동기화 컴포넌트가
auth 상태 변화(로그인 사용자 id 가 바뀜)를 보고 처리한다. 마지막으로 본 사용자 id 를
localStorage 에 남겨 두어, 앱이 꺼져 있는 동안 세션이 끝난 경우도 다음 실행 때 잡는다.
못 민 것을 지우지 않는 이유는 확인 없이 데이터를 잃지 않기 위해서고, 남는 것은
반영되지 않은 변경뿐이라 공용 PC 에 남는 양이 최소가 된다.

**결정(구현자 아님, 대화 중 Claude 의 판단)**: 처음 사용자에게 "로그아웃해도 사본이
남는다"고 안내했으나, 공용 PC 반목표 때문에 로그아웃 시 지우는 쪽으로 바꿨다. 서버에
남아 있으므로 잃는 것이 아니다. 단 로그아웃 시점에 밀지 못한 변경(오프라인)은 잃을
수 있다 — 이때는 로그아웃 전에 "아직 저장되지 않은 변경이 있어요" 확인을 띄운다.

### 4.5 실패를 보여주기

동기화 상태를 루틴 화면 상단에 한 줄로 보여준다.
- 로그인 안 함: 지금 문구("이 브라우저에만 저장돼요") + 설정으로 가는 링크
- 동기화됨: "계정에 저장돼요"
- 밀기 실패가 남아 있음: "아직 계정에 저장되지 않았어요 · 다시 시도"

밀기는 실패하면 `dirty` 로 남고, 다음 당기기·포커스·변경 때 다시 시도한다. 백오프는
구현자에게 맡긴다.

### 4.6 코드 자리

- 저장 매체를 아는 코드가 둘이 된다: 로컬은 `routines.ts`, 서버는 새 파일
  `features/routines/routineSync.ts`. 병합 함수는 순수 함수로 따로 두고 단위 테스트한다.
  AGENTS.md 의 "저장 매체를 아는 코드는 routines.ts 안에만" 문장을 이 둘로 고친다.
- 로그인 상태 감시와 당기기·밀기 시작은 루트 레이아웃에 붙는 클라이언트 컴포넌트 하나가
  맡는다(피드에서도 담기가 일어나므로 탭 레이아웃만으로는 부족하다).
- 서버 호출은 브라우저 anon 클라이언트 + RLS 로 한다. 라우트 핸들러를 새로 만들지 않는다.
  `service` 클라이언트는 절대 쓰지 않는다.

## 5. 운동 기록

### 5.1 무엇을 기록하나

루틴 재생에서 **마지막 운동이 끝나면** "운동 1회"를 기록한다. 끝 감지는 실패할 수
있으므로, 루틴 재생의 마지막 슬라이드에는 항상 "운동 완료" 버튼을 함께 둔다. 둘 중
먼저 일어난 것이 기록하고, 같은 재생에서 두 번 기록하지 않는다.

기록 한 건: `{ id, routineId, routineName, completedAt, localDate }`.
- `localDate`(YYYY-MM-DD)는 **기록한 기기의 현지 날짜**다. 자정 근처, 시간대가 다른
  기기 사이에서도 "그날 운동했다"가 사용자가 느낀 날짜로 남는다. 통계는 이 값으로 센다.
- `routineName` 을 복사해 둔다. 루틴을 지우거나 이름을 바꿔도 기록이 뜻을 잃지 않는다.

### 5.2 보여주기

루틴 화면 맨 위, 루틴 목록 위에 카드 하나.
- 이번 주(월~일) 7칸. 운동한 날은 라임으로 채운다. 오늘은 테두리로 표시한다.
- 연속 일수: 오늘 또는 어제까지 하루도 빠짐없이 운동한 날 수. 오늘 아직 안 했어도
  어제까지 이어졌으면 끊기지 않은 것으로 센다.
- 이번 달 횟수.
- 기록이 하나도 없으면 카드 대신 한 줄: "루틴을 끝까지 하면 여기에 기록돼요."

### 5.3 저장과 동기화

로컬: `health-shorts:workouts:v1`. 기록은 추가만 된다(편집·삭제 없음).

서버: `public.workout_logs(user_id, id, routine_id, routine_name, completed_at, local_date)`,
기본키 `(user_id, id)`. RLS 는 본인 select/insert 만. 추가만 되므로 병합은 id 합집합이다.
`owner` 규칙, 흡수 확인(루틴과 한 번에 묻는다), 세션 종료 시 정리는 루틴과 같다.
사용자당 같은 `local_date` 기록 20건 상한을 트리거로 걸고 로컬에서도 같은 값으로 막는다.
상한에 걸린 기록은 그냥 기록하지 않는다 — 하루 20번 넘게 루틴을 끝내는 것은 사람이
아니다.

통계 계산은 순수 함수로 두고 단위 테스트한다(주 경계, 월 경계, 연속 일수가 어제에서
끊기는 경우, 하루 여러 번).

## 6. 검증

- 단위: 병합 규칙, v1→v2 변환, owner 필터, 통계 함수.
- E2E 는 Supabase 없이 돈다(`playwright.config.ts` 가 빈 값을 강제). 비로그인 경로의
  회귀(루틴 담기·재생·지우기·되돌리기)와 운동 기록 표시를 E2E 로 지킨다.
- 동기화 왕복은 E2E 로 못 한다. `scripts/check-auth.ts` 처럼 실제 Supabase 를 상대로
  RLS(남의 행이 안 보이고 못 쓰는지)와 upsert 를 확인하는 점검 스크립트를 더한다.
- 수동 확인 목록(README): 두 브라우저에서 같은 계정으로 담기·지우기가 넘어가는지,
  비로그인 루틴이 첫 로그인 때 들어가는지, 로그아웃 후 루틴이 사라지고 다시 로그인하면
  돌아오는지.

## 7. 구현자에게 맡기는 것

- 밀기 재시도 간격, 포커스 시 당기기의 최소 간격.
- 동기화 상태 줄과 운동 기록 카드의 세부 모양(기존 `components/ui` 프리미티브와 토큰
  안에서).
- 마이그레이션 파일 번호와 정책 이름.
- 로그아웃 전 확인의 형태(대화상자 또는 인라인).
